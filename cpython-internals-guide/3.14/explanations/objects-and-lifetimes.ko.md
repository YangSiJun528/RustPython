# 바인딩, 변경, 객체 수명은 서로 다른 문제다

Python의 이름과 슬롯에는 값 자체가 아니라 객체를 가리키는 참조가 들어간다. 이름을 다시 대입하는 바인딩 변경은 화살표를 다른 객체로 돌리고, 리스트에 항목을 추가하는 변경은 화살표가 가리키는 객체의 내용을 바꾼다. 이 차이를 잡으면 함수 인수, closure, 지역 변수와 객체 수명을 같은 모델로 설명할 수 있다.

객체의 수명은 그 객체를 가리키는 이름의 개수가 아니라 소유권을 가진 강한 참조로 결정된다. 일반적인 GIL 빌드의 참조 횟수 경로에서는 마지막 강한 참조가 사라질 때 객체를 바로 정리하고, 서로를 붙잡아 참조 횟수가 0이 되지 않는 순환은 cyclic GC로 찾는다. 자유 스레딩 빌드는 biased·deferred reference counting 때문에 실제 정리가 늦어질 수 있다.

이 글은 일반적인 CPython 3.14 개념을 설명한다. 실제 참조 상태의 표현은 GIL 빌드와 자유 스레딩 빌드에서 다르며, 관찰한 참조 횟수를 곧바로 소유 참조의 정확한 개수나 객체 정리 시점으로 해석하면 안 된다.

## 모든 값은 타입을 가진 객체로 표현된다

정수, 문자열, 리스트, 함수, 코드 객체는 모두 `PyObject` 계열이다. 구체 객체의 앞부분에는 타입과 수명 관리에 필요한 공통 정보가 있고, 뒤에는 각 타입의 데이터가 놓인다.

```text
구체 객체
┌──────────────────────┐
│ PyObject 공통 정보   │  타입·참조 상태
├──────────────────────┤
│ 타입별 데이터        │  숫자·문자·항목·바이트코드 등
└──────────────────────┘
```

일반 지역 변수 슬롯도 객체 전체를 품지 않는다. 현재 객체를 가리키는 내부 참조를 보관한다. CPython 3.14의 평가 스택과 일부 Frame 필드는 `_PyStackRef` 같은 표현을 쓰므로, 모든 내부 참조를 단순한 소유 `PyObject *`라고 단정해서는 안 된다.

## 재바인딩은 화살표를 바꾸고 변경은 대상을 바꾼다

```py
a = []
b = a
a.append(1)
a = []
```

`b = a` 뒤에는 두 이름이 같은 리스트를 가리킨다. `append`는 그 리스트를 바꾸므로 `b`에서도 `[1]`이 보인다. 마지막 `a = []`은 `a`만 새 리스트에 묶는다. 기존 리스트의 내용과 `b`의 바인딩은 그대로다.

closure cell도 같은 원리다. `PyCellObject`는 현재 값 객체를 가리키는 공유 가능한 바인딩 저장소다. `nonlocal x`에 다시 대입하면 cell의 화살표가 바뀌고, `x.append(...)`는 cell이 가리키는 리스트를 바꾼다.

## 참조 소유권이 보통의 객체 수명을 결정한다

강한 참조는 객체가 살아 있도록 책임진다. Frame의 지역 슬롯, 리스트의 항목, 함수의 `__code__`와 `__closure__`처럼 다른 객체를 보관하는 곳이 강한 참조를 가질 수 있다. C API의 빌린 참조는 다른 소유자가 수명을 보장하는 동안만 사용할 수 있으며, 필요 이상으로 해제하거나 소유자가 사라진 뒤 사용해서는 안 된다.

```text
마지막 강한 참조 해제
        ↓
참조 횟수 0
        ↓
타입의 deallocation 함수가 정리
```

객체를 가리키는 C 포인터를 한 번 복사했다고 언제나 참조 횟수가 늘어나는 것은 아니다. `new reference`, `borrowed reference`, `steals a reference` 같은 API 계약이 누가 생존을 책임지는지 정한다. 일부 객체는 불멸 객체여서 보통의 0 도달 규칙으로 정리되지 않는다.

## cyclic GC는 참조 횟수만으로 찾지 못하는 순환을 처리한다

```text
A ──→ B
↑     │
└─────┘
```

외부에서 A와 B에 도달할 수 없어도 내부 참조 때문에 각 참조 횟수는 0보다 클 수 있다. cyclic GC는 GC 추적 대상 가운데 이런 도달 불가능한 순환을 찾아 정리한다. 참조 횟수가 0인 모든 객체를 나중에 GC가 회수하는 방식은 아니다.

예외가 traceback을, traceback이 Frame을, Frame의 지역 변수가 다시 예외를 가리키면 실제 순환이 만들어진다. 실행이 끝난 Frame의 `frame.clear()`는 지역 참조를 지워 이 순환을 끊을 수 있다. 반대로 지역 객체 하나를 따로 보관했다고 그 객체가 원래 Frame을 거꾸로 살려 두는 것은 아니다.

설명한다.
