# PEG 파서는 순서 있는 선택으로 토큰에서 AST 하나를 만든다

CPython 3.14의 파서는 문법 대안을 집합처럼 다루지 않는다. 현재 토큰 위치에서
대안을 적힌 순서대로 시도하고, 처음 성공한 대안을 선택한다. 이 **순서 있는
선택** 덕분에 겹치는 문법에서도 결과가 하나로 정해진다.

백트래킹만 순진하게 반복하면 같은 구간을 여러 번 읽어 비용이 커진다. Pegen은
필요한 규칙의 결과를 메모이제이션하고 왼쪽 재귀를 별도로 처리한다. 성공한
규칙의 action은 AST를 만들며, 문법 오류는 정상 규칙과 `invalid_` 규칙을 나눈
두 번의 파싱으로 더 정확하게 보고한다.

> 이 글은 CPython 3.14의 Pegen을 설명한다. PEG 일반론과 CPython의 구체적인
> 메모이제이션·오류 처리 방식을 같은 것으로 일반화하면 안 된다.

## Pegen은 문자보다 먼저 정리된 토큰을 받는다

일반적인 PEG 파서는 문자 스트림을 직접 읽을 수 있지만 CPython은 토크나이저와
파서를 분리한다.

```text
소스 문자
  ↓ CPython tokenizer
NAME, NUMBER, NEWLINE, INDENT, DEDENT, ...
  ↓ Pegen으로 생성한 parser
AST
```

Python은 들여쓰기, 인코딩, 대화형 입력, 닫히지 않은 괄호처럼 별도 처리가 필요한
요소가 많다. 토크나이저가 이들을 토큰으로 정리하고, 파서는 토큰 배열에서 문법
규칙을 적용한다.

## 먼저 성공한 대안이 해석을 확정한다

다음 규칙에서 `A`가 성공하면 `B`는 시도하지 않는다.

```text
rule: A | B
```

그래서 `A | B`와 `B | A`는 결과가 달라질 수 있다. 더 큰 규칙이 나중에
실패하더라도, 이미 성공한 내부 선택을 다시 열어 다른 대안으로 바꾸지 않는다.
공통 접두사를 가진 대안은 어느 쪽이 먼저 성공하는지 따져 배치해야 한다.

```text
잘못되기 쉬운 순서
  'if' expression 'then' block
| 'if' expression 'then' block 'else' block

의도에 맞는 순서
  'if' expression 'then' block 'else' block
| 'if' expression 'then' block
```

첫 번째 규칙에서는 짧은 대안이 먼저 성공해 `else`가 있는 긴 대안을 가린다.

## lookahead와 cut은 선택이 확정되는 경계를 조정한다

긍정 lookahead `&e`와 부정 lookahead `!e`는 입력 위치를 움직이지 않고 다음 입력의
모양을 검사한다. cut `~`를 지난 뒤 실패하면 같은 규칙의 다른 대안으로 돌아가지
않는다.

lookahead는 경계를 분명히 할 수 있지만 일반 문법 오류 위치에도 영향을 줄 수 있다.
cut은 탐색을 줄이고 구체적인 오류를 유지할 수 있지만 너무 일찍 두면 유효한 다른
대안을 막는다. 둘 다 문법의 의미를 바꾸는 제어 장치다.

## 메모이제이션은 필요한 규칙에만 적용된다

백트래킹 중 같은 `(규칙, 토큰 위치)`를 다시 계산하면 비용이 반복된다. 캐시에는
성공 여부뿐 아니라 다음 토큰 위치와 생성된 AST 조각도 들어갈 수 있다.

전형적인 packrat 설명과 달리 CPython의 C 파서는 모든 규칙을 무조건 캐시하지 않는다.
문법에서 `(memo)`로 지정한 규칙만 선택적으로 메모이제이션한다. 캐시 조회와 메모리
사용 자체에도 비용이 있기 때문이다. 다만 왼쪽 재귀 규칙은 그 처리 알고리즘이 캐시에
의존하므로 항상 메모이제이션된다.

왼쪽 재귀는 규칙의 맨 왼쪽에서 자신을 다시 참조하는 구조다.

```text
expr: expr '+' term | term
```

순진한 재귀 하강 파서는 입력을 소비하기 전에 다시 `expr()`를 호출해 무한 재귀에
빠진다. Pegen은 캐시된 결과를 바탕으로 더 긴 일치가 나오지 않을 때까지 결과를
확장하는 방식으로 이를 처리한다.

## action은 인식된 구문을 AST 값으로 바꾼다

Pegen 규칙은 성공 여부만 반환하지 않는다. 하위 규칙의 결과에 이름을 붙이고,
대안 뒤의 action에서 AST 노드를 만들 수 있다.

```text
expr[expr_ty]:
    | l=expr '+' r=term { _PyAST_BinOp(l, Add, r, EXTRA) }
    | term
```

문법은 어떤 토큰열이 유효한지 결정하고, action은 이미 인식된 구문을 어떤 AST로
표현할지 결정한다. 일반적인 규칙을 action 안에서 다시 검사해 받아들이거나 거부하면
공개 문법과 실제 CPython 동작이 어긋난다.

메모이제이션된 AST가 다른 탐색 경로에서 재사용될 수도 있다. 따라서 action은 전달받은
AST 노드를 제자리에서 바꾸지 말고, 변경이 필요하면 새 노드를 만들어야 한다.

## 구문 오류는 정상 실패와 예외를 구분해 만든다

규칙 실패는 흔히 다음 대안을 시도하라는 정상 제어 흐름이다. 반면 action이나 C API가
예외를 설정하면 파싱을 중단하고 예외를 전파한다.

정상 규칙만으로 전체 파싱에 실패했을 때 CPython은 두 번째 패스를 실행한다.

```text
1차: 정상 규칙만 사용
├─ 성공 → AST 반환
└─ 실패
   ↓
2차: 정상 규칙 + invalid_ 규칙
├─ 잘못된 패턴 감지 → 구체적인 SyntaxError
└─ 감지 못함 → 1차 패스의 일반 오류 위치 사용
```

`invalid_` 규칙은 오류 AST를 만드는 규칙이 아니라 알려진 잘못된 패턴을 알아보고
정확한 `SyntaxError`를 내기 위한 규칙이다.
