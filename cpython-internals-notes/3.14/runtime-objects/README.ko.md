## 대상 독자와 읽는 방법

독자가 nand2tetris를 수료해 스택 기반 가상 머신, 함수 호출 프레임,
명령어 주소와 상수 테이블의 기본 역할은 알고 있다고 가정한다.
따라서 일반적인 VM 구조를 처음부터 설명하기보다는 CPython의 code
object, interpreter frame, generator 중단·재개, 문자열 인터닝처럼
구체적인 구현 개념에 집중한다.

원문의 제목, 문장, 목록, 표와 코드 예제를 원래 순서대로 모두
번역한다. 문맥만으로 뜻이 충분한 부분에는 번역만 제시하고,
CPython의 객체 수명이나 참조 소유권처럼 별도 배경지식이 필요한
부분에는 다음 형식의 해설을 붙인다.

> **해설:** 이 형식의 문단은 원문 번역이 아니라 독자를 위한 추가 설명이다.

이 문서는 Python 언어 명세가 아니라 **CPython 3.14의 내부 구현**
설명이다. 다른 Python 구현이나 다른 CPython 버전에는 그대로 적용되지
않을 수 있다.

## 전체 지도

네 문서는 실행 중인 Python 프로그램을 서로 다른 각도에서 설명한다.

1. **Code Objects**: 컴파일 결과인 실행 명세는 어떤 데이터를
   가지는가?
2. **Generators and Coroutines**: 실행을 중단했다가 다시 시작하는
   함수는 프레임을 어떻게 보존하는가?
3. **Frames**: 한 번의 함수 실행에 필요한 가변 상태는 어디에
   저장되는가?
4. **String Interning**: 반복해서 쓰이는 문자열을 하나의 대표 객체로
   합쳐 조회 비용을 어떻게 줄이는가?

```text
Python 소스
    ↓ 컴파일
code object ── 호출 ──→ interpreter frame ── 실행
                         │
                         └─ 중단·재개 ─→ generator

이름·속성 문자열 ── interning ─→ 대표 문자열 객체 ─→ 빠른 dict/속성 조회
```

> **nand2tetris와의 대응:** nand2tetris VM에서 함수 호출 때마다
> `local`, `argument`, `this`, `that` 등의 실행 상태가 달라지는 것처럼,
> CPython에서도 같은 함수 코드를 여러 번 호출하면 호출마다 별도의
> frame이 생긴다. 변하지 않는 명령과 상수 정보는 code object에 두고,
> 호출마다 변하는 값과 실행 위치는 frame에 둔다는 분리가 핵심이다.

## 제1부: 코드 객체

> 원문: [CPython 3.14 `InternalDocs/code_objects.md`](https://github.com/python/cpython/blob/3.14/InternalDocs/code_objects.md)

`CodeObject`는 컴파일된 함수나 클래스처럼, 컴파일을 마쳐 실행할 수 있는 대상을 표현하는
Python 내장 타입이다.

코드 객체에는 바이트코드 명령어 열과 그에 딸린 메타데이터가 함께 들어 있다. 메타데이터에는
명령이 접근할 상수의 값처럼 바이트코드 실행에 꼭 필요한 데이터도 있고, 디버거나 기타 도구가
사용하는 소스 코드 위치 같은 문맥 정보도 있다.

> **해설 — 바이트코드만으로 충분하지 않은 이유**
>
> `LOAD_CONST 2`라는 명령만 보아서는 무엇을 불러올지 알 수 없다. 코드 객체의 상수
> 테이블에서 인덱스 2를 함께 봐야 한다. 마찬가지로 traceback이 소스의 줄과 열을 표시하려면
> 현재 바이트코드 위치를 소스 위치에 연결하는 정보가 필요하다. `CodeObject`는 명령 배열만
> 담은 파일이 아니라, 그 명령을 해석하는 데 필요한 묶음 전체다.

Python 3.11부터 `PyCodeObject` C 구조체의 마지막 필드는 길이가 미리 정해지지 않은 배열이며,
바이트코드는 `code->co_code_adaptive`에 들어 있다. 이전 버전에서는
[`bytes`](https://docs.python.org/dev/library/stdtypes.html#bytes) 객체인
`code->co_code`에 바이트코드를 보관했다. 추가 할당 한 번을 없애고, 실행 중 내용을 바꿀 수
있게 하려고 현재 구조로 변경했다.

> **해설 — 구조체 마지막의 가변 길이 배열**
>
> C 구조체 본체와 바이트코드 저장 공간을 한 덩어리로 할당하는 방식이다. 구조체 선언만
> 보면 배열 길이가 고정되어 있지 않지만, 실제 객체를 만들 때 필요한 바이트코드 길이만큼
> 뒤쪽 공간을 더 확보한다. 이 덕분에 별도 `bytes` 객체와 그 객체를 가리키는 포인터를
> 할당할 필요가 없다.

코드 객체는 일반적으로 바이트코드
[컴파일러](https://github.com/python/cpython/blob/3.14/InternalDocs/compiler.md)가 만든다.
다만 한 프로세스가
코드 객체를 디스크에 기록하고, 이후 다른 프로세스가 다시 읽는 경우도 흔하다. 디스크에
저장되는 코드 객체는
[`marshal`](https://docs.python.org/dev/library/marshal.html) 프로토콜로 직렬화된다.

> **해설 — `marshal` 직렬화**
>
> 메모리 안의 코드 객체에는 포인터와 C 구조체처럼 그대로 파일에
> 쓸 수 없는 값이 있다. 직렬화는 이 구조를 나중에 다시 복원할 수
> 있는 바이트열로 바꾸는 과정이다. `marshal`은 CPython이 코드
> 객체와 `.pyc` 파일 같은 내부 데이터를 저장하는 데 사용하는
> 형식이며, 장기간 호환되는 범용 데이터 교환 형식으로 보면 안 된다.

`CodeObject`가 생성되면
[`Python/specialize.c`](https://github.com/python/cpython/blob/3.14/Python/specialize.c)의
`_PyCode_Quicken()`을 호출하여 모든
adaptive instruction의 캐시를 초기화한다. 디스크 형식은 바이트의 연속인데, 캐시 가운데
일부는 16비트 초기값을 필요로 하므로 이 초기화 과정이 필요하다.

> **해설 — adaptive instruction과 캐시**
>
> CPython은 같은 바이트코드를 반복 실행하며 관찰한 타입 등의 정보를 이용해 명령을 더
> 구체적인 빠른 형태로 특수화할 수 있다. 명령 가까이에 놓인 inline cache가 그 관찰 결과를
> 저장한다. 디스크에는 이 런타임 상태가 완성된 형태로 저장되지 않으므로, 코드 객체를
> 메모리에 올릴 때 `_PyCode_Quicken()`이 캐시 슬롯을 실행 가능한 초기 상태로 만든다.

코드 객체는 명목상 불변 객체다. `co_code_adaptive`와 `_co_monitoring` 같은 런타임 정보
필드를 포함하여 실제로 변경 가능한 필드도 있지만, 코드 객체의 해시를 계산하거나 두 코드
객체를 비교할 때에는 이러한 가변 필드를 포함하지 않는다.

> **해설 — “명목상 불변”의 의미**
>
> Python 프로그램이 보는 코드의 의미는 불변으로 취급하지만, 인터프리터 내부 최적화와
> 모니터링 상태는 실행 중 달라질 수 있다. 가변 캐시까지 동등성 비교에 넣으면 같은 소스에서
> 만들어진 코드 객체도 실행 이력에 따라 서로 다르다고 판정될 수 있다. 그래서 의미를
> 나타내는 필드와 런타임 가속 상태를 구분한다.

### 소스 코드 위치

예외가 발생할 때 인터프리터는 현재 프레임에 대한 traceback 항목을 예외에 추가한다. 호출
스택을 되감는 동안 지나가는 각 프레임에 대해서도 항목을 하나씩 추가한다.

traceback 항목의 `tb_lineno` 필드는 예외가 발생한 순간 해당 프레임에서 실행 중이던 명령의
줄 번호로 설정된다. 이 값은 필요할 때 계산하는 지연 방식으로 채워진다.

줄 번호는 locations table인 `co_linetable`과
[`PyCode_Addr2Line`](https://docs.python.org/dev/c-api/code.html#c.PyCode_Addr2Line)
함수를 이용해 계산한다. 이름에는 line만 들어 있지만 `co_linetable`은 줄 번호보다 더 많은
정보를 담는다. 각 명령마다 다음 네 값으로 정확한 소스 범위를 나타낸다.

1. 시작 줄
2. 끝 줄
3. 시작 열
4. 끝 열

명령마다 이 네 값을 저장하면 데이터가 상당히 커질 수 있으므로, 압축된 형식이 매우 중요하다.

> **해설 — 위치 정보가 명령마다 필요한 이유**
>
> 한 소스 줄이 여러 바이트코드 명령을 만들 수 있고, 한 표현식이 여러 줄에 걸칠 수도 있다.
> 줄 번호 하나만으로는 `obj.method(arg)` 중 어느 부분에서 문제가 생겼는지 정밀하게 표시할
> 수 없다. 시작·끝 줄과 열을 모두 알면 traceback의 오류 범위 표시와 디버깅 도구가 더
> 정확해진다.

traceback 객체 자체가 이 위치 정보를 전부 저장하는 것은 아니다. 하위 버전과의 호환을 위해
시작 줄 번호를 저장하고, 여기에 “마지막 명령” 값도 저장한다. 나머지 위치 정보는 마지막
명령을 나타내는 `tb_lasti`와 locations table을 이용해 계산할 수 있다.

Python 코드에서는 편의를 위해
[`codeobject.co_positions`](https://docs.python.org/dev/reference/datamodel.html#codeobject.co_positions)
메서드를 제공한다. 이 메서드는 명령마다 하나씩
`({line}, {endline}, {column}, {endcolumn})` 튜플을 내놓는 이터레이터를 반환한다.

`co_lines()`도 제공한다. 이 메서드는
`({start}, {end}, {line})` 튜플의 이터레이터를 반환하며, 여기서 `{start}`와 `{end}`는
바이트코드 오프셋이다. 이 인터페이스는
[`PEP 626`](https://peps.python.org/pep-0626/)에서 설명한다. `co_lines()`의 결과는 더
간결하지만 끝 줄 번호나 열 오프셋은 반환하지 않는다.

C 코드에서는
[`PyCode_Addr2Location`](https://docs.python.org/dev/c-api/code.html#c.PyCode_Addr2Location)을
호출해야 한다.

> **해설 — `tb_lasti`**
>
> `tb_lasti`는 예외 당시 프레임이 실행하던 바이트코드 위치를 가리킨다. traceback에 네 개의
> 소스 위치 값을 복사해 넣는 대신, 이 실행 위치와 코드 객체의 공용 위치 테이블을 함께
> 사용한다. 같은 정보를 프레임마다 중복 저장하지 않는 설계다.

locations table은 traceback을 표시할 때와 tracing 중 추적 함수에 줄 번호를 전달할 때만
조회한다. 따라서 일반 실행 경로에서 조회 성능이 결정적으로 중요하지는 않다.

다만 tracing 중 발생하는 부담을 줄이기 위해, 명령 오프셋에서 줄 번호로 가는 매핑을
`_co_linearray` 필드에 캐시한다.

#### locations table의 형식

코드 객체의 `co_linetable` `bytes` 객체는 명령어의 소스 위치를 압축해서 표현한다.
`co_positions()` 이터레이터가 반환하는 위치 정보의 근원이 바로 이 데이터다.

> **참고**
>
> `co_linetable`과 `co_lnotab`을 혼동하면 안 된다. 하위 버전 호환을 위해 `co_lnotab`은
> Python 3.10 이하에서 사용하던 형식을 노출한다. 이 과거 형식은 각 명령의 시작 줄만
> 저장한다. `co_lnotab`에 접근하면 `co_linetable`로부터 지연 생성된다. 자세한 내용은
> [`Objects/lnotab_notes.txt`](https://github.com/python/cpython/blob/3.14/Objects/lnotab_notes.txt)를
> 참고한다.

`co_linetable`은 location entry가 연속된 형태다. 각 entry의 첫 바이트는 최상위 비트가
1이며, 그 뒤에는 최상위 비트가 0인 바이트가 0개 이상 이어진다.

각 entry에는 다음 정보가 들어 있다.

- 이 entry가 담당하는 code unit의 수, 즉 길이
- 시작 줄
- 끝 줄
- 시작 열
- 끝 열

첫 바이트의 형식은 다음과 같다.

| Bit 7 | Bits 3-6 | Bits 0-2 |
|---|---|---|
| 1 | Code | Length(code unit 단위) - 1 |

`Code` 값의 종류는 `_PyCodeLocationInfoKind` enum에 열거되어 있다.

> **해설 — 첫 바이트를 표식과 데이터로 함께 사용한다**
>
> Bit 7의 1은 새 location entry의 시작임을 표시한다. 중간 바이트들은 Bit 7이 0이므로,
> 바이트 열을 순서대로 읽다가 다음 Bit 7이 1인 바이트를 만나면 다음 entry가 시작되었음을
> 알 수 있다. 나머지 비트에는 위치 표현 방식인 `Code`와 이 entry가 몇 code unit을
> 담당하는지가 들어간다.

> **해설 — code unit**
>
> code unit은 CPython이 바이트코드를 배치하고 오프셋을 계산할 때 사용하는 내부 고정 크기
> 단위다. 하나의 Python 소스 연산이나 하나의 논리 명령과 반드시 일대일로 대응하지 않는다.
> 확장 인자나 inline cache가 추가 code unit을 차지할 수 있기 때문이다. 여기서 길이는 소스
> 문자 수나 AST 노드 수가 아니라 바이트코드 저장 단위의 수다.

#### 가변 길이 정수 인코딩

정수는 가변 길이 정수 인코딩을 사용해 저장하는 경우가 많다.

##### 부호 없는 정수(`varint`)

부호 없는 정수는 하위 부분부터 6비트씩 잘라 저장한다. 마지막 조각을 제외한 각 조각에서는
Bit 6을 1로 설정한다.

예시는 다음과 같다.

- 63은 `0x3f`로 인코딩한다.
- 200은 `0x48`, `0x03`으로 인코딩한다.
  `200 = (0x03 << 6) | 0x48`이기 때문이다.

다음 보조 함수를 사용해 정수를 `varint`로 변환할 수 있다.

```py
def encode_varint(s):
    ret = []
    while s >= 64:
        ret.append(((s & 0x3F) | 0x40) & 0x3F)
        s >>= 6
    ret.append(s & 0x3F)
    return bytes(ret)
```

> **해설 — 원문의 예제 코드와 설명이 일치하지 않는다**
>
> 위 코드는 원문을 그대로 보존했다. 그러나 `| 0x40`으로 Bit 6을 켠 직후 `& 0x3F`를
> 적용하면 Bit 6이 다시 지워진다. 따라서 200에 대해 설명에 나온 `0x48`이 아니라
> `0x08`을 첫 바이트로 만든다. 문장과 예시에 맞는 전형적인 구현이라면 마지막 마스크가
> `& 0x7F`이거나 아예 없어야 한다. CPython 3.14 문서 자체의 오타로 보이며, 실제 형식을
> 구현할 때 이 함수를 검증 없이 사용하면 안 된다.

`varint`를 부호 없는 정수로 되돌리는 함수는 다음과 같다.

```py
def decode_varint(chunks):
    ret = 0
    for chunk in reversed(chunks):
        ret = (ret << 6) | chunk
    return ret
```

> **해설 — 하위 조각 우선**
>
> 첫 바이트에 가장 낮은 6비트가 들어가므로, 사람이 흔히 보는 큰 자릿수 우선 표기와
> 반대다. 디코딩 함수는 조각 순서를 뒤집은 뒤, 이미 모은 값에 6비트 자리를 만들고 다음
> 조각을 합친다. Bit 6은 “뒤에 조각이 더 있다”는 표식이므로 실제 구현에서는 entry를
> 나누는 과정과 값 비트 처리 규칙을 함께 따라야 한다.

##### 부호 있는 정수(`svarint`)

부호 있는 정수는 먼저 다음 함수로 부호 없는 정수에 대응시킨 뒤 인코딩한다.

```py
def svarint_to_varint(s):
    if s < 0:
        return ((-s) << 1) | 1
    else:
        return s << 1
```

`varint`에서 부호 있는 정수로 되돌리는 함수는 다음과 같다.

```py
def varint_to_svarint(uval):
    return -(uval >> 1) if uval & 1 else (uval >> 1)
```

> **해설 — 부호를 최하위 비트에 넣는다**
>
> 음수는 홀수, 0과 양수는 짝수로 대응된다. 예를 들면 `0 → 0`, `-1 → 3`,
> `1 → 2`, `-2 → 5`다. 값의 부호와 크기를 한 부호 없는 정수에 넣은 뒤 기존 `varint`
> 형식을 재사용하려는 방식이다.

#### Location entry

`Code` 값과 뒤따르는 바이트의 의미는 다음과 같다.

| Code | 의미 | 시작 줄 | 끝 줄 | 시작 열 | 끝 열 |
|---|---|---|---|---|---|
| 0-9 | 짧은 형식 | Δ 0 | Δ 0 | 아래 설명 참고 | 아래 설명 참고 |
| 10-12 | 한 줄 형식 | Δ (`code - 10`) | Δ 0 | 부호 없는 1바이트 | 부호 없는 1바이트 |
| 13 | 열 정보 없음 | Δ `svarint` | Δ 0 | `None` | `None` |
| 14 | 긴 형식 | Δ `svarint` | Δ `varint` | `varint` | `varint` |
| 15 | 위치 없음 | `None` | `None` | `None` | `None` |

표의 Δ는 다른 값을 기준으로 한 차이, 즉 delta로 값을 인코딩한다는 뜻이다.

- 시작 줄: 이전 entry의 시작 줄과의 차이다. 첫 entry라면 `co_firstlineno`와의 차이다.
- 끝 줄: 해당 entry의 시작 줄과의 차이다.

> **해설 — delta 인코딩**
>
> 인접한 바이트코드 명령은 같은 줄이나 가까운 줄에서 나오는 경우가 많다. 절대 줄 번호가
> 5000이어도 이전 시작 줄이 4999라면 저장할 값은 1이다. 작은 값일수록 `varint`가 적은
> 바이트를 사용하므로 전체 위치 테이블이 작아진다. `Δ 0`은 기준값과 같아 별도 변화가
> 없음을 뜻한다.

> **해설 — 위치 정보가 없는 명령**
>
> Code 15는 컴파일러가 삽입했지만 대응하는 소스 범위가 없는
> 명령처럼, 위치를 제공할 수 없는 경우를 표현한다.

#### 짧은 형식

Code 0부터 9까지는 짧은 형식이다. 짧은 형식은 두 바이트로 구성되며, 두 번째 바이트에 추가
열 정보를 넣는다. 이때 `Code`는 시작 열을 8로 나눈 뒤 내림한 값이다.

- 시작 열: `(code*8) + ((second_byte>>4)&7)`
- 끝 열: `start_column + (second_byte&15)`

> **해설 — 두 번째 바이트의 비트 배치**
>
> 두 번째 바이트의 상위 쪽 3비트는 `code*8`에서 시작 열이 얼마나 더 떨어져 있는지
> 나타낸다. 하위 4비트는 시작 열부터 끝 열까지의 길이를 나타낸다. 자주 나타나는 짧은
> 단일 줄 표현식의 위치를 두 바이트만으로 기록하기 위한 특수 압축 형식이다. 시작 열을
> 8개씩 묶어 `Code`에 넣으므로 Code 0-9는 시작 열 0-79 범위를 효율적으로 다룬다.

## 제2부: 제너레이터와 코루틴

> 원문: [CPython 3.14 InternalDocs — Generators and Coroutines](https://github.com/python/cpython/blob/3.14/InternalDocs/generators.md)

### 제너레이터

CPython에서 제너레이터는 `PyGenObject` 구조체로 구현된다. 이 구조체는 [`frame`](https://github.com/python/cpython/blob/3.14/InternalDocs/frames.md)과 제너레이터의 실행 상태를 나타내는 메타데이터로 이루어진다.

> **해설 — `frame`**
>
> 프레임은 함수 한 번의 실행에 필요한 상태 묶음이다. 현재 실행할
> 바이트코드 위치, 지역 변수, 평가 스택 등을 보관한다. 일반 함수는
> 호출을 마치면 같은 실행을 재개할 필요가 없다. 프레임 객체가
> 외부에 노출된 경우에는 호출 후에도 일부 상태가 남을 수 있지만,
> 제너레이터는 정상 동작 자체를 위해 `yield` 시점의 실행 상태를
> 보존해야 한다.

제너레이터 객체의 `send()` 메서드를 호출하면 제너레이터는 자신의 프레임에서 실행을 재개한다. 이는 함수가 호출될 때 자기 프레임 안에서 실행되는 것과 비슷하다. 다만 함수는 실행을 마친 뒤 호출한 프레임으로 한 번만 돌아가지만, 제너레이터는 [`yield` 표현식](https://docs.python.org/dev/reference/expressions.html#yield-expressions)으로 새 항목을 내놓을 때마다 호출자의 프레임으로 실행 제어권을 넘긴다.

이 동작은 [`YIELD_VALUE`](https://docs.python.org/dev/library/dis.html#opcode-YIELD_VALUE) 바이트코드로 구현된다. `YIELD_VALUE`는 값을 스택에 놓고 호출 프레임에 실행 제어권을 돌려준다는 점에서 [`RETURN_VALUE`](https://docs.python.org/dev/library/dis.html#opcode-RETURN_VALUE)와 비슷하다. 그러나 제너레이터 프레임을 나중에 재개할 수 있는 상태로 남겨 두기 위한 추가 작업도 수행해야 한다. 구체적으로 프레임의 명령어 포인터를 갱신하고, 인터프리터의 예외 상태를 제너레이터 객체에 저장한다. 제너레이터를 다시 시작할 때는 이 예외 상태를 인터프리터 상태로 되돌려 복사한다.

> **해설 — `yield`는 단순한 조기 `return`이 아니다**
>
> `RETURN_VALUE` 뒤에는 같은 함수 실행을 다시 이어 갈 수 없다. 반면 `YIELD_VALUE`는 다음에 실행할 명령어 위치와 그 시점의 실행 문맥을 남긴다. 예외 상태까지 저장하는 이유는 제너레이터가 멈춰 있는 동안 호출자 쪽에서 예외 처리 상태가 달라져도, 제너레이터 내부의 `try`/`except` 문맥을 정확히 복원해야 하기 때문이다. 여기서 스택은 CPU의 하드웨어 스택이 아니라 CPython 바이트코드가 사용하는 프레임별 평가 스택을 가리킨다.

제너레이터의 `frame`은 제너레이터 객체 구조체 안에 [`_PyInterpreterFrame`](https://github.com/python/cpython/blob/3.14/InternalDocs/frames.md) 형태로 내장된다. 자세한 정의는 [`pycore_genobject.h`](https://github.com/python/cpython/blob/3.14/Include/internal/pycore_genobject.h)의 `_PyGenObject_HEAD`에서 볼 수 있다. 이 구조 덕분에 제너레이터에서 프레임을 찾을 수도 있고, 반대로 프레임에서 그 프레임을 품고 있는 제너레이터를 찾을 수도 있다. 같은 파일의 `_PyGen_GetGeneratorFromFrame`이 후자의 예다. 제너레이터 구조체의 다른 필드에는 제너레이터 함수의 이름 같은 메타데이터와, 프레임이 실행 중인지·중단되었는지·정리되었는지 등을 나타내는 런타임 상태 정보가 들어 있다.

> **해설 — 프레임을 “내장한다”는 의미**
>
> 제너레이터 객체가 프레임을 가리키는 별도 포인터만 갖는 것이 아니라, 프레임용 메모리가 제너레이터 객체의 메모리 배치 안에 포함된다는 뜻이다. `_PyGen_GetGeneratorFromFrame`은 이 고정된 배치 관계를 이용해 내부 프레임 주소에서 바깥 제너레이터 객체를 찾는다.

### 제너레이터 객체의 생성과 파괴

제너레이터 함수의 바이트코드는 [`RETURN_GENERATOR`](https://docs.python.org/dev/library/dis.html#opcode-RETURN_GENERATOR) 명령어로 시작한다. 이 명령어는 내장 프레임을 포함하는 제너레이터 객체를 만든다. 제너레이터 프레임은 `RETURN_GENERATOR`를 실행 중인 프레임을 복사해 초기화하지만, `owner` 필드는 그 프레임의 소유자가 제너레이터임을 나타내도록 덮어쓴다.

마지막으로 `RETURN_GENERATOR`는 새 제너레이터 객체를 스택에 올리고 제너레이터 함수를 호출한 쪽으로 돌아간다. 이때 `RETURN_GENERATOR`를 실행하던 원래 프레임은 파괴된다. 이후 [`gen_send_ex2()`](https://github.com/python/cpython/blob/3.14/Objects/genobject.c)로 제너레이터를 재개하면 `_PyEval_EvalFrame()`이 호출되고, 제너레이터 객체 안에 내장된 프레임에서 제너레이터 함수의 나머지 실행을 이어 간다.

> **해설 — 제너레이터 함수를 호출해도 본문이 바로 실행되지 않는 이유**
>
> 일반 함수 호출은 곧바로 본문을 실행하지만, 제너레이터 함수 호출의 첫 결과는 제너레이터 객체다. `RETURN_GENERATOR`가 현재 실행 준비 상태를 제너레이터 객체 내부로 옮기고 즉시 호출자에게 돌아가기 때문이다. 실제 본문은 처음 `next()`나 `send()`가 호출될 때 진행된다. `owner`는 해당 `_PyInterpreterFrame`의 수명과 정리를 누가 책임지는지 나타내는 내부 소유권 표지다.

[`gen_dealloc`](https://github.com/python/cpython/blob/3.14/Objects/genobject.c)에서 제너레이터 객체를 파괴할 때, 제너레이터 안의 `_PyInterpreterFrame`이 [`PyFrameObject`](https://github.com/python/cpython/blob/3.14/InternalDocs/frames.md#frame-objects)의 일부로 Python 코드에 노출되어 있다면 그 프레임을 보존해야 할 수 있다. [`_PyFrame_ClearExceptCode`](https://github.com/python/cpython/blob/3.14/Python/frame.c)는 인터프리터 프레임의 `frame_obj` 필드가 설정되어 있고, 그 필드가 가리키는 프레임 객체의 참조 횟수가 1보다 큰지를 검사해 이 상황을 알아낸다. 조건이 맞으면 `take_ownership()`을 호출해 인터프리터 프레임의 새 복사본을 만들고, 프레임의 소유권을 제너레이터에서 프레임 객체로 넘긴다.

> **해설 — 객체는 사라져도 관찰 중인 프레임은 살아 있어야 한다**
>
> `generator.gi_frame`이나 디버깅·검사 기능을 통해 Python 수준의 프레임 객체를 다른 코드가 보관할 수 있다. 이 상태에서 제너레이터 메모리와 함께 내장 프레임을 없애면 남아 있는 `PyFrameObject`가 무효 메모리를 가리키게 된다. 참조 횟수가 1보다 크다는 것은 제너레이터 내부 연결 외에도 프레임을 붙잡고 있는 사용자가 있다는 뜻이다. 그래서 독립된 복사본을 만들고 프레임 객체가 그 수명을 책임지게 한다.

### 반복

[`FOR_ITER`](https://docs.python.org/dev/library/dis.html#opcode-FOR_ITER) 명령어는 스택 맨 위의 반복자에 `__next__`를 호출하고 결과를 다시 스택에 올린다. 이 명령어에는 몇 가지 흔한 반복자 타입을 위한 [`specialization`](https://github.com/python/cpython/blob/3.14/InternalDocs/interpreter.md)이 있으며, 제너레이터를 반복하는 `FOR_ITER_GEN`도 그중 하나다. `FOR_ITER_GEN`은 `__next__` 호출을 거치지 않고 제너레이터 프레임을 실행 체인에 직접 푸시해 연결한 다음, 마지막 `yield` 바로 다음 명령어부터 실행을 재개한다.

> **해설 — 특수화**
>
> 일반 `FOR_ITER`는 어떤 종류의 반복자도 처리해야 하므로 동적인
> `__next__` 호출 절차를 사용한다. 실행 중 반복자가
> 제너레이터라는 사실을 확인하면 `FOR_ITER_GEN`이라는 더 좁고
> 빠른 경로를 사용할 수 있다. Python 수준 메서드 호출과 타입 판별
> 일부를 건너뛰고, 저장되어 있던 제너레이터 프레임을 현재 실행
> 체인에 직접 연결해 재개하는 최적화다.

### 연결된 제너레이터

`yield from` 표현식은 다른 제너레이터가 만드는 값의 흐름을 효율적으로 그대로 내보내는 제너레이터를 만든다. 이 동작은 [`SEND` 명령어](https://docs.python.org/dev/library/dis.html#opcode-SEND)로 구현된다. `SEND`는 자신의 인자 값을 연결된 제너레이터의 프레임 스택에 올리고, 그 프레임에 예외 상태를 설정한 뒤 연결된 제너레이터의 실행을 재개한다.

`SEND`에서 돌아오면 스택 맨 위의 값이 `YIELD_VALUE`를 통해 제너레이터 연결의 위쪽 호출자로 다시 전달된다. 제너레이터가 더 내놓을 값이 없음을 알리는 `StopIteration` 예외가 발생할 때까지 `SEND` 다음에 `YIELD_VALUE`가 이어지는 순서를 반복한다.

> **해설 — `yield from`을 단순한 `for` 루프로만 보면 빠지는 것**
>
> 값만 차례로 전달하는 상황에서는 `for value in child: yield value`와 비슷해 보인다. 그러나 `yield from`은 호출자가 보낸 값과 예외, 하위 제너레이터의 종료 값까지 제너레이터 사슬을 따라 전달해야 한다. `SEND`는 이 양방향 위임을 바이트코드 수준에서 처리한다.

[`CLEANUP_THROW`](https://docs.python.org/dev/library/dis.html#opcode-CLEANUP_THROW) 명령어는 이 send-yield 반복 과정에서 발생한 예외를 처리한다. `StopIteration` 타입의 예외는 정상 종료 신호로 처리하며, 그 예외의 `value` 필드에는 제너레이터의 `close()` 함수가 반환할 값이 들어 있다. 다른 종류의 예외는 `CLEANUP_THROW`가 다시 발생시킨다.

> **해설 — `CLEANUP_THROW`의 실제 적용 범위**
>
> 위 원문은 `CLEANUP_THROW`를 send-yield 반복의 예외 처리로 넓게
> 설명한다. [CPython 3.14
> 구현](https://github.com/python/cpython/blob/3.14/Python/bytecodes.c)에서
> 이 명령은 `throw()`나 `close()`로 제너레이터 사슬에 예외를
> 주입한 경로를 정리할 때 사용된다. 일반 `SEND` 중 발생한
> `StopIteration`은 `SEND` 자체가 처리한다.
>
> `CLEANUP_THROW` 경로에서는 `StopIteration.value`를 정상 결과로
> 꺼내고, 다른 예외는 다시 발생시킨다. 제너레이터 내부의
> `return value`가 `StopIteration(value)`로 전달된다는 기본 원리는
> 같지만, 모든 정상적인 `yield from` 종료를 이 명령 하나가
> 처리한다고 이해하면 안 된다.

### 코루틴

코루틴은 `yield` 표현식이 돌려주는 값을 사용하는 제너레이터다. 여기서 그 값은 제너레이터가 값을 내놓은 뒤 다시 시작될 때 `.send()` 호출에 전달된 인자다. 이를 통해 데이터가 양방향으로 흐를 수 있다. 제너레이터에서 호출자로는 `yield` 표현식에 지정한 값이 전달되고, 호출자에서 제너레이터로는 `send()` 호출의 인자가 전달된다.

`yield from` 표현식은 `send` 인자를 연결된 제너레이터에 넘기므로, 이 양방향 데이터 흐름은 제너레이터 사슬 전체에서 동작한다. 구현은 [`genobject.c`](https://github.com/python/cpython/blob/3.14/Objects/genobject.c)의 `gen_send_ex2()`를 참고할 수 있다.

> **해설 — `yield` 표현식에는 들어오는 값도 있다**
>
> `received = yield outgoing`에서 `outgoing`은 호출자가 받는 값이고, 다음 `send(incoming)`의 `incoming`은 중단되었던 `yield` 표현식의 결과가 되어 `received`에 들어간다. 따라서 `yield`는 한 방향의 출력 명령이 아니라, 실행을 중단하는 지점을 사이에 둔 양방향 통신 지점으로 볼 수 있다.

제너레이터의 `__next__` 함수는 단순히 `self.send(None)`을 호출한다는 점을 기억하자. 따라서 제너레이터와 코루틴 모두 같은 재개 메커니즘으로 동작하지만, `send` 인자의 값을 실제 계산에 사용하는 쪽은 코루틴이다.

> **해설 — 여기서 말하는 코루틴의 범위**
>
> 이 문단은 제너레이터 기반의 중단·재개와 `send()` 데이터 흐름을 중심으로 코루틴을 설명한다. 현대 Python의 `async def`로 만드는 네이티브 코루틴은 별도의 객체 종류와 문법을 갖지만, CPython 내부에서는 제너레이터와 많은 프레임·중단·재개 메커니즘을 공유한다. “모든 제너레이터는 값을 내보낼 수 있지만, 코루틴은 다시 들어오는 값까지 통신에 사용한다”는 실행 모델에 초점을 맞추면 된다.

## 제3부: 프레임

> 원문: [CPython 3.14 — Frames](https://github.com/python/cpython/blob/3.14/InternalDocs/frames.md)

Python 함수를 한 번 호출할 때마다 활성화 레코드(activation record)가 하나 생긴다. 이를 보통 “프레임(frame)”이라고 부른다. 프레임에는 실행 중인 함수에 관한 정보가 들어 있으며, 개념적으로 다음 세 영역으로 구성된다.

- 지역 변수. 인수, 셀 변수, 자유 변수를 포함한다.
- 평가 스택.
- 특수 필드. VM이 프레임별로 필요로 하는 객체 참조와 값이다. 전역 딕셔너리, 코드 객체, 명령어 포인터, 스택 깊이, 이전 프레임 등이 여기에 포함된다.

> **해설 — 활성화 레코드와 세 영역**
>
> 같은 함수를 재귀적으로 세 번 호출하면 함수 코드는 하나지만 프레임은 세 개다. 호출마다 인수, 지역 변수, 계산 중간값, 돌아갈 위치가 달라지기 때문이다. nand2tetris에서 함수 호출마다 스택에 새 프레임을 만들던 것과 같은 개념이다.
>
> CPython의 “평가 스택”에는 바이트코드 연산의 중간값이 놓인다. 예를 들어 두 값을 읽어 덧셈하기 전에는 피연산자들이 이 스택에 있다. “셀 변수”와 “자유 변수”는 클로저를 위한 변수다. 내부 함수가 바깥 함수의 지역 변수를 계속 참조할 수 있도록 일반 지역 변수와 다른 보관 방식을 사용한다.

`_PyInterpreterFrame` 구조체의 정의는 [`Include/internal/pycore_interpframe_structs.h`](https://github.com/python/cpython/blob/3.14/Include/internal/pycore_interpframe_structs.h)에 있다.

> **해설 — `_PyInterpreterFrame`**
>
> 이것은 CPython 인터프리터 내부에서 실제 실행 상태를 담는 C 구조체다. 이름 앞의 `_Py`와 `Include/internal` 경로가 나타내듯 안정적인 공개 C API가 아니라 CPython 내부 구현 세부사항이다.

### 할당

Python의 의미 규칙상 프레임은 해당 함수 호출의 실행이 끝난 뒤에도 살아남을 수 있으므로 C 호출 스택 바깥에 할당해야 한다. 오버헤드를 줄이고 참조 지역성을 높이기 위해 대부분의 프레임은 스레드별 스택에 연속해서 할당된다. [`Python/pystate.c`](https://github.com/python/cpython/blob/3.14/Python/pystate.c)의 `_PyThreadState_PushFrame`을 참고하라.

> **해설 — 왜 C 호출 스택만으로는 부족한가**
>
> 일반적인 C 지역 변수는 함수가 반환하면 더 이상 유효하지 않다. 그러나 Python에서는 `sys._getframe()`, 트레이스백, 디버거 등을 통해 호출이 끝난 뒤에도 프레임 정보가 필요할 수 있다. 제너레이터와 코루틴은 실행 도중 멈췄다가 나중에 재개되므로 실행 상태 자체가 C 함수 호출보다 오래 산다.
>
> 여기서 “스레드별 스택”은 운영체제가 제공하는 C 호출 스택과 구분해야 한다. CPython이 각 스레드 상태에 연결해 직접 관리하는 프레임 저장 영역이다. 프레임을 연속 배치하면 할당 횟수가 줄고, 서로 가까운 메모리를 반복해서 읽으므로 CPU 캐시에도 유리하다. 이것이 “참조 지역성”이다.

제너레이터와 코루틴의 프레임은 제너레이터 객체와 코루틴 객체 안에 내장되므로 스레드별 스택에는 할당되지 않는다. [`Include/internal/pycore_interpframe_structs.h`](https://github.com/python/cpython/blob/3.14/Include/internal/pycore_interpframe_structs.h)의 `_PyGenObject`를 참고하라.

> **해설**
>
> 제너레이터와 코루틴은 `yield` 또는 `await`에서 멈춘 상태로 오래 존재할 수 있다. 프레임을 해당 객체 안에 넣으면 객체와 실행 상태의 수명이 자연스럽게 같아지고, 객체와 프레임을 따로 할당할 필요도 없다.

#### 배치

각 활성화 레코드는 다음 순서로 배치된다.

- 특수 필드
- 지역 변수
- 스택

이 배치는 지나치게 복잡하지 않으면서 가장 좋은 성능을 내는 것으로 보인다. 특수 필드의 크기는 고정되어 있으므로 지역 변수 영역의 오프셋을 알 수 있다. 인터프리터는 프레임 포인터와 스택 포인터, 두 포인터를 유지해야 한다.

> **해설 — 메모리 배치와 두 포인터**
>
> 하나의 프레임을 단순화하면 다음처럼 볼 수 있다.
>
> ```text
> 낮은 주소
> ┌──────────────────────┐ ← 프레임 포인터가 기준으로 삼는 위치
> │ 고정 크기 특수 필드  │
> ├──────────────────────┤ ← 고정 오프셋으로 지역 변수 시작점을 계산
> │ 지역 변수 슬롯       │
> ├──────────────────────┤
> │ 평가 스택            │
> │ ...                  │
> └──────────────────────┘ ← 스택 포인터
> 높은 주소
> ```
>
> 프레임 포인터는 현재 프레임의 기준 위치를, 스택 포인터는 평가 스택의 현재 꼭대기를 가리킨다. 특수 필드가 고정 크기이므로 별도의 “지역 변수 포인터” 없이도 지역 변수 슬롯을 찾을 수 있다.

##### 대안적 배치

3.11 알파 개발 기간 일부에 사용했던 대안적 배치는 다음과 같다.

- 지역 변수
- 특수 필드
- 스택

이 배치에는 함수를 호출할 때 복사가 필요 없다는 장점이 있다. 스택 위의 인수들이 보통 이미 매개변수에 맞는 위치에 놓여 있기 때문이다. 그러나 VM이 지역 변수용 포인터를 하나 더 유지해야 하므로 성능이 나빠질 수 있다.

> **해설 — 복사를 줄이는 대신 포인터가 늘어난다**
>
> 호출 직전에는 호출자의 평가 스택에 함수 인수가 연속해서 놓여 있다. 새 프레임의 맨 앞이 지역 변수 영역이면 이 인수 메모리를 매개변수 슬롯으로 그대로 활용하기 쉽다. 반면 특수 필드가 지역 변수와 스택 사이에 들어가므로, 프레임 기준 주소만으로 지역 변수와 평가 스택을 모두 간단히 추적하기 어렵다.
>
> 추가 포인터 하나가 언제나 느리다는 뜻은 아니다. 자주 실행되는 인터프리터 루프에서 레지스터 하나를 계속 차지하고 관리해야 하는 비용과 인수 복사 절감 효과를 실제로 측정했을 때, 현재 배치가 더 나았다는 설명이다.

##### 특수 필드

특수 필드 영역에는 다음 포인터들이 들어 있다.

- 전역 딕셔너리
- 내장 이름 딕셔너리
- 지역 딕셔너리. “빠른” 지역 변수가 아니라 `eval`과 클래스 생성에 사용하는 지역 변수 딕셔너리다.
- 코드 객체
- 이 활성화 레코드에 힙 할당된 `PyFrameObject`가 있다면 그 객체
- 함수

> **해설 — 빠른 지역 변수와 지역 딕셔너리**
>
> 보통 함수의 지역 변수는 문자열 키로 매번 딕셔너리를 조회하지 않고, 컴파일 때 정해진 번호의 슬롯에서 직접 읽고 쓴다. 이를 “fast locals”라고 부른다. 반면 `eval()`이나 클래스 본문 실행처럼 이름 공간을 딕셔너리 형태로 다뤄야 하는 경우에는 별도의 지역 딕셔너리가 필요하다.
>
> 코드 객체는 실행할 바이트코드와 상수·이름 메타데이터를 담고, 함수 객체는 여기에 전역 네임스페이스·기본 인수·클로저 같은 실행 문맥을 결합한다. 프레임은 특정 함수 객체가 특정 호출에서 실행되는 현재 상태다.

함수 포인터가 반드시 필요한 것은 아니다. 그러나 전역 딕셔너리와 내장 이름 딕셔너리 양쪽에 강한 참조를 보관하는 것보다 함수에 강한 참조 하나를 보관하고 전역 딕셔너리와 내장 이름 딕셔너리에는 빌린 참조를 보관하는 편이 더 저렴하다.

> **해설 — 강한 참조와 빌린 참조**
>
> CPython은 주로 참조 횟수로 객체 수명을 관리한다. 강한 참조는 참조 횟수를 올려 객체가 살아 있도록 보장한다. 빌린 참조는 참조 횟수를 올리지 않으므로, 다른 소유자가 객체의 수명을 보장해야 한다.
>
> 함수 객체가 살아 있으면 그 함수가 참조하는 전역 딕셔너리와 내장 이름 환경도 유효하다는 관계를 이용한다. 그래서 함수 하나만 강하게 소유하고 나머지는 빌려 쓰면 참조 횟수 증감 작업과 소유권 관리 비용을 줄일 수 있다.

##### 프레임 객체

백트레이스를 만들거나 `sys._getframe()`을 호출하면 프레임이 Python 코드에 보이게 된다. 이때 새 `PyFrameObject`를 만들고, 그 객체에 대한 강한 참조를 특수 필드 영역의 `frame_obj` 필드에 넣는다. `frame_obj` 필드의 초기값은 `NULL`이다.

> **해설 — 내부 프레임과 Python에 노출되는 프레임**
>
> `_PyInterpreterFrame`은 실행에 최적화한 내부 표현이고, `PyFrameObject`는 `frame.f_code`, `frame.f_lineno`처럼 Python 코드와 디버깅 도구가 관찰할 수 있는 힙 객체다. 모든 호출마다 처음부터 `PyFrameObject`까지 만들면 비용이 크므로, 실제로 외부 관찰이 필요해질 때만 지연 생성한다.

`PyFrameObject`는 스택에 할당된 `_PyInterpreterFrame`보다 오래 살아남을 수 있다. 그런 경우 평가 스택을 제외한 `_PyInterpreterFrame`을 `PyFrameObject` 안으로 복사한다. 이 시점에는 평가 스택이 비어 있어야 한다. 이전 프레임 링크는 프레임의 새 위치를 반영하도록 갱신한다.

> **해설 — 프레임의 소유권 이전**
>
> 이 문단의 “스택에 할당”은 앞에서 설명한 CPython 관리 스레드별 스택을 뜻한다. 그 저장 영역은 호출이 끝나면 재사용되므로, `PyFrameObject`가 더 오래 살아야 한다면 필요한 내부 상태를 힙 객체가 소유하는 저장 공간으로 옮겨야 한다.
>
> 프레임들은 “이전 프레임” 링크로 호출 관계를 이룬다. 저장 주소가 바뀌면 다른 프레임이나 프레임 객체가 낡은 주소를 가리키지 않도록 링크도 바꿔야 한다. 평가 스택이 비어 있어야 한다는 제약 덕분에 실행 중간값까지 복사하고 소유권을 조정하는 복잡성을 피한다.

이 메커니즘은 각 활성화마다 영속적인 힙 할당 프레임이 존재하는 것처럼 보이게 하면서도 런타임 오버헤드를 낮게 유지한다.

> **해설**
>
> 사용자 관점에서는 프레임이 언제나 독립적인 Python 객체처럼 보인다. 구현에서는 대부분의 호출을 저렴한 내부 프레임만으로 처리하고, 관찰되거나 오래 살아야 하는 프레임에만 힙 객체 비용을 지불한다.

##### 제너레이터와 코루틴

제너레이터, 즉 타입이 `PyGen_Type`, `PyCoro_Type`, `PyAsyncGen_Type`인 객체에는 `_PyInterpreterFrame`이 내장되어 있다. 따라서 한 번의 메모리 할당만으로 객체를 만들 수 있다. 이렇게 내장된 프레임을 순회하거나 await할 때는 링크 필드를 통해 스레드별 스택의 프레임들과 연결할 수 있다.

> **해설 — 내장되어 있지만 실행 중에는 호출 체인에 연결된다**
>
> 정지해 있을 때 제너레이터 프레임은 제너레이터 객체 안에 보관된다. `next()`, `send()`, `await` 등으로 실행을 재개하면 현재 호출자의 프레임과 연결되어 정상적인 호출 체인과 트레이스백에 참여한다. 실행을 다시 양보하면 객체 안에 상태를 유지한 채 호출 체인에서 빠질 수 있다.

제너레이터와 연결된 프레임 객체가 제너레이터보다 오래 살아남으면, 내장된 `_PyInterpreterFrame`을 프레임 객체 안으로 복사한다. [`Python/frame.c`](https://github.com/python/cpython/blob/3.14/Python/frame.c)의 `take_ownership()`을 참고하라.

> **해설**
>
> 원래 내부 프레임을 소유하던 제너레이터가 먼저 해제되면 그 안의 메모리도 사라진다. 프레임 객체가 계속 유효하려면 `take_ownership()`이 필요한 상태를 프레임 객체 쪽으로 이전한다.

##### 필드 이름

`_PyInterpreterFrame`의 여러 필드는 3.10의 `PyFrameObject`에서 복사해 왔다. 따라서 일부 필드 이름은 조금 오해를 일으킬 수 있다.

예를 들어 `f_globals` 필드는 `_PyInterpreterFrame` 구조체에 속하지만, `f_` 접두사는 마치 `PyFrameObject` 구조체에 속하는 것처럼 보이게 한다. 이후 버전에서 이 명명 체계를 더 합리적으로 정리할 수도 있다.

> **해설**
>
> CPython 3.11에서 실행용 내부 프레임과 Python에 노출되는 프레임 객체의 역할을 더 분리하면서 이전 이름이 남은 결과다. 여기서 `f_`를 보고 반드시 `PyFrameObject`의 필드라고 추론하면 안 된다.

##### 심 프레임

`_PyEval_EvalFrameDefault()`에 진입할 때 심(shim) `_PyInterpreterFrame` 하나를 푸시한다. 이 프레임은 C 스택에 저장되며 `_PyEval_EvalFrameDefault()`가 반환할 때 팝된다. 이 추가 프레임을 삽입하면 `RETURN_VALUE`, `YIELD_VALUE`, `RETURN_GENERATOR`가 현재 프레임이 진입 프레임인지 검사할 필요가 없다. 심 프레임은 `INTERPRETER_EXIT` 명령어가 들어 있는 특수 코드 객체를 가리킨다. 이 명령어는 심 프레임을 정리하고 반환한다.

> **해설 — 경계 조건을 보통 경로로 바꾸는 센티널**
>
> 인터프리터 평가 루프의 맨 바깥 프레임이 반환할 때는 돌아갈 일반 Python 호출자가 없다. 매 반환 명령에서 “호출자가 있는가?”를 검사하는 대신, 가짜 호출자 역할을 하는 심 프레임을 하나 둔다.
>
> ```text
> 심 프레임: INTERPRETER_EXIT
>     ↓ 호출한 것처럼 연결
> 실제 진입 프레임
>     ↓
> 그 아래 Python 호출들
> ```
>
> 실제 프레임이 반환하면 일반적인 상위 프레임 복귀 절차를 그대로 밟아 심 프레임의 `INTERPRETER_EXIT`에 도착한다. 이는 목록 끝에 센티널 값을 두어 반복문의 특수 분기를 없애는 기법과 비슷하다. 여기서만 심 프레임이 C 스택에 놓인다는 점도, 앞서 말한 대부분의 `_PyInterpreterFrame`이 C 호출 스택 바깥에 있다는 설명과 구분해야 한다.

##### 명령어 포인터

`_PyInterpreterFrame`에는 명령어 포인터를 유지하는 데 사용하는 두 필드 `instr_ptr`와 `return_offset`이 있다.

프레임을 실행 중일 때 `instr_ptr`는 현재 실행 중인 명령어를 가리킨다. 정지된 프레임에서는 프레임을 재개할 때 실행하게 될 명령어를 가리킨다. `frame.f_lineno`를 설정한 뒤에는 `instr_ptr`가 다음에 실행할 명령어를 가리킨다. Python 함수를 호출하는 동안에는 `instr_ptr`가 호출 명령어를 가리킨다. 예외 트레이스백에서 볼 것으로 기대하는 위치가 바로 이 호출 명령어이기 때문이다.

> **해설 — 하나의 필드가 상태에 따라 가리키는 위치**
>
> `instr_ptr`의 의미는 항상 단순한 “다음 PC”가 아니다.
>
> - 실행 중: 현재 명령어
> - `yield` 등으로 정지: 재개할 명령어
> - `frame.f_lineno` 변경 직후: 다음에 실행할 명령어
> - 하위 Python 함수 호출 중: 호출자의 호출 명령어
>
> 특히 호출 중에 포인터를 이미 호출 다음으로 옮기지 않는 이유는, 하위 함수에서 예외가 발생했을 때 트레이스백이 “호출자가 어느 호출 표현식을 실행하다 실패했는가”를 가리켜야 하기 때문이다.

`return_offset` 필드는 피호출자가 `RETURN`할 때 호출자의 어느 위치로 이동할지를 `instr_ptr`에 대한 상대 위치로 결정한다. 이 필드는 피호출자에게만 의미가 있다. 따라서 Python 함수를 호출하는 명령어를 구현할 때마다 이 값을 설정해야 한다. 이러한 명령어에는 `CALL`, `SEND`, `BINARY_OP_SUBSCR_GETITEM` 등이 있다. 피호출자가 없다면 `return_offset`에는 의미가 없다. 반환 오프셋에 별도 필드가 필요한 이유는 다음과 같다. (1) `RETURN`을 실행하는 동안 이 오프셋을 `instr_ptr`에 적용하면 너무 이르다. 그러면 인트로스펙션과 디버깅에 필요할 수 있는 이전 명령어 정보가 사라진다. (2) `SEND`는 제너레이터에 두 오프셋을 전달해야 한다. 하나는 `RETURN`용이고 다른 하나는 `YIELD`용이다. 둘 중 하나에는 `oparg`를 사용하고 다른 하나에는 `return_offset`을 사용한다.

> **해설 — 반환 주소를 즉시 PC에 적용하지 않는 이유**
>
> nand2tetris의 호출 규약에서는 복귀 주소를 저장했다가 함수가 끝날 때 그 주소로 점프했다. 여기서도 기본 생각은 같다. 다만 CPython은 호출자의 `instr_ptr`를 호출 명령어에 그대로 두어 디버깅에 필요한 “현재 호출 위치”를 보존하고, 실제 복귀 거리는 피호출자 프레임의 `return_offset`에 따로 둔다.
>
> `return_offset`은 절대 주소가 아니라 호출자의 `instr_ptr`를 기준으로 한 상대 오프셋이다. `CALL`뿐 아니라 제너레이터를 진행하는 `SEND`, 특수화된 구독 조회 경로인 `BINARY_OP_SUBSCR_GETITEM`도 Python 프레임 호출을 일으킬 수 있어 값을 설정해야 한다.
>
> `SEND`는 제너레이터가 끝나 `RETURN`한 경우와 값을 내놓아 `YIELD`한 경우에 호출자가 서로 다른 지점으로 진행해야 한다. 바이트코드 명령어의 피연산자인 `oparg`와 프레임의 `return_offset` 두 저장 장소를 사용해 두 목적지를 함께 전달한다.

## 제4부: 문자열 인터닝

> 원문: [CPython 3.14 `InternalDocs/string_interning.md`](https://github.com/python/cpython/blob/3.14/InternalDocs/string_interning.md)

*인터닝된(interned)* 문자열은 개념적으로 인터프리터 전역의
*인터닝 문자열 집합*에 속한다. 이는 다음을 뜻한다.

- 한 인터프리터 안에서는 내용이 같은 인터닝 문자열 객체가 둘 이상
  존재하지 않는다.
- 인터닝 문자열 두 개는 포인터 동일성, 즉 Python의 `is`로 안전하게
  비교할 수 있다.

이 성질은 딕셔너리와 속성 조회 등을 최적화하는 데 사용된다.

Python은 문자열을 인터닝하는 데 싱글턴과 동적 인터닝이라는 두 가지
메커니즘을 사용한다.

> **해설 — 문자열 값 비교를 포인터 비교로 바꾸기**
>
> 일반적인 문자열 비교는 길이와 각 문자를 확인해야 한다. 하지만
> 내용이 같은 인터닝 문자열이 반드시 같은 객체라면 두 포인터만
> 비교해도 값이 같은지 알 수 있다. 변수 이름과 속성 이름처럼 같은
> 문자열을 반복해서 조회하는 경로에서 이 최적화가 효과적이다.
>
> 여기서 `is`를 사용해도 안전하다는 말은 CPython 내부의 **인터닝된
> 문자열끼리** 비교할 때의 이야기다. 일반 Python 코드에서 문자열 값
> 비교를 `==` 대신 `is`로 해도 된다는 뜻은 아니다.

### 싱글턴

가능한 한 글자 Latin-1 문자열 256개는 `_Py_LATIN1_CHR(c)`로 가져올
수 있다. 이 객체들은 정적으로 할당된 다음 배열에 저장된다.

- `_PyRuntime.static_objects.singletons.strings.ascii`
- `_PyRuntime.static_objects.singletons.strings.latin1`

더 긴 싱글턴 문자열은 C 소스에서 `_Py_ID` 또는 `_Py_STR`로
표시한다. 문자열이 유효한 C 식별자의 일부라면 `_Py_ID`를 사용하고,
C에서 사용할 별도의 이름이 필요하다면 `_Py_STR`을 사용한다. 이
문자열들도 정적으로 할당된 배열에 저장된다.

`make regen-global-objects`를 실행하면
`Tools/build/generate_global_objects.py`가 CPython 소스에서 이
문자열들을 수집하고 선언, 초기화, 종료 처리 코드를 생성한다.

빈 문자열도 싱글턴 중 하나이며 `_Py_STR(empty)`로 나타낸다.

세 싱글턴 집합 `_Py_LATIN1_CHR`, `_Py_ID`, `_Py_STR`은 서로
겹치지 않는다. 이 중 하나에 속하는 싱글턴이 있다면 바로 그 객체만
인터닝되며, 같은 내용을 가진 다른 복사본은 인터닝되지 않는다.

이 싱글턴들은 런타임을 초기화할 때 런타임 전역 조회 테이블인
`_PyRuntime.cached_objects.interned_strings`, 즉
`INTERNED_STRINGS`에 인터닝된다. 이 테이블은 런타임 종료 과정에서
해체될 때까지 변경되지 않는다. 따라서 별도의 동기화 없이 스레드와
인터프리터 사이에서 공유된다.

> **해설 — 정적 싱글턴과 동적 문자열의 범위**
>
> 여기서 “런타임 전역”은 하나의 CPython 런타임에 속한 여러
> 인터프리터가 같은 싱글턴 객체를 공유한다는 뜻이다. 초기화가 끝난
> 뒤 테이블을 수정하지 않으므로, 여러 스레드가 동시에 읽어도
> 테이블 변경 경쟁이 발생하지 않는다.
>
> Latin-1 한 글자 문자열은 Unicode 코드 포인트 U+0000부터
> U+00FF까지의 256개 문자열이다. 자주 쓰이는 짧은 문자열을 실행
> 중에 매번 새로 할당하지 않도록 CPython 실행 파일 안에 미리
> 마련해 둔다고 이해하면 된다.

### 동적으로 할당되는 문자열

그 밖의 모든 문자열은 동적으로 할당되며
`_PyUnicode_STATE(s).statically_allocated` 플래그가 0으로
설정된다. 이런 문자열을 인터닝하면 인터프리터 전역 딕셔너리인
`PyInterpreterState.cached_objects.interned_strings`에 추가된다.

이 딕셔너리의 각 항목에서 키와 값은 같은 객체를 참조한다.

> **해설 — 딕셔너리를 집합처럼 사용한다**
>
> 논리적으로 필요한 것은 대표 문자열들의 집합이지만, 내부에서는
> 키와 값이 같은 딕셔너리 항목으로 저장한다. 따라서 평범한
> 딕셔너리 참조 계산만 보면 같은 문자열에 키와 값에서 각각 하나씩,
> 총 두 개의 참조가 생긴다. 이 두 참조가 다음 절의 특수한 참조
> 횟수 처리와 연결된다.

### 불멸성과 참조 횟수 관리

GIL을 사용하는 빌드에서는 인터닝 문자열이 소멸 가능할 수도 있고
불멸 객체일 수도 있다. 자유 스레딩 빌드에서는 인터닝 문자열이 항상
불멸 객체다.

> **해설 — GIL 빌드와 자유 스레딩 빌드**
>
> GIL 빌드는 한 인터프리터에서 Python 바이트코드를 실행하는
> 스레드를 전역 잠금으로 제한하는 일반적인 CPython 구성이다. 자유
> 스레딩 빌드는 이 GIL을 비활성화하여 여러 스레드가 Python 코드를
> 병렬로 실행할 수 있게 한 구성이다. 이 문단은 두 구성에서 인터닝
> 문자열의 수명 정책이 다르다는 사실만 설명하며, 그 이유까지
> 규정하지는 않는다.

소멸 가능한 인터닝 문자열은 다음과 같이 처리한다.

- 인터닝 딕셔너리의 키와 값에서 생기는 참조 두 개를 해당 문자열의
  참조 횟수에서 제외한다.
- 소멸자 `unicode_dealloc`이 문자열을 인터닝 딕셔너리에서 제거한다.
- 종료 시 인터닝 딕셔너리를 비울 때는 제외했던 참조를 다시 참조
  카운트에 더한다.

> **해설 — 딕셔너리가 객체를 영원히 붙잡지 않게 하기**
>
> 딕셔너리의 키와 값 참조를 평범한 강한 참조로 계산하면, 외부에서
> 문자열을 아무도 사용하지 않아도 인터닝 딕셔너리 자신이 문자열을
> 계속 붙잡는다. CPython은 이 두 내부 참조를 참조 횟수에서
> 제외하여 외부의 마지막 소유 참조가 사라질 때 `unicode_dealloc`이
> 실행될 수 있게 한다. 소멸자는 해당 항목을 딕셔너리에서도
> 제거한다.
>
> 종료할 때는 딕셔너리가 평범한 방식으로 키와 값을 해제할 수 있도록
> 제외했던 두 참조를 먼저 복구한다. 이는 일반적인 Python 객체의
> 참조 횟수 관리보다 낮은 수준의 내부 구현 기법이다.

다른 타입과 마찬가지로 인터프리터가 종료될 때까지 살아 있을
문자열만 불멸 객체로 만들어야 한다.

현재는 코드 객체 등에 들어 있는 문자열도 컴파일러와 `marshal`에서
불멸 객체로 만든다. 이 문자열들은 불멸 객체로 간주해도 “충분히
가깝다.” 핫 리로딩이나 사용자 입력을 `eval`하는 경우에도 서로 다른
식별자와 문자열 상수의 수는 적은 수준에 머물 것으로 예상하기
때문이다.

> **해설 — 불멸 객체의 비용**
>
> 불멸 객체는 사용처가 사라져도 인터프리터 종료 전에는 해제되지
> 않는다. 따라서 입력에 따라 끝없이 새로운 문자열이 생기는 경로를
> 무조건 불멸화하면 메모리 사용량이 계속 증가할 수 있다. 코드
> 객체의 식별자와 상수는 종류가 비교적 제한적이라는 경험적 판단
> 아래 이 비용을 허용한다.

### 내부 API

문자열 인터닝에는 다음 *내부* API를 사용한다.

- `_PyUnicode_InternMortal`: 문자열을 인터닝하기만 한다.
- `_PyUnicode_InternImmortal`: 문자열을 인터닝하고 그 결과를 불멸
  객체로 만든다.
- `_PyUnicode_InternStatic`: 정적 싱글턴 `_Py_STR`, `_Py_ID` 또는
  한 바이트 문자열을 인터닝한다. 일반 용도로 사용해서는 안 된다.

세 함수 모두 인터프리터 상태와 `PyObject *`를 가리키는 포인터를
받으며, 전달받은 포인터가 가리키는 값을 제자리에서 변경한다.

이 함수들은 인자로 받은 참조의 소유권을 가져가고, 인자를 *새로운*
참조로 갱신한다. 이는 다음을 의미한다.

- 참조 수 관점에서 “중립적(reference neutral)”이다.
- 빌린 참조를 인자로 전달해서는 안 된다.

> **해설 — `PyObject **`와 참조 소유권**
>
> 호출자가 강한 참조 하나를 소유한 `PyObject *s`를 가지고 있다면
> 함수에는 `&s`를 전달한다. 함수는 기존 `s`의 참조 하나를
> 소비하고, 실제 대표 인터닝 객체를 가리키는 새로운 강한 참조
> 하나를 다시 `s`에 넣는다. 호출 전후에 호출자가 소유한 참조가
> 하나라는 점은 같으므로 “참조 중립적”이다.
>
> 빌린 참조는 호출자가 소유한 참조가 아니므로 함수가 가져갈 수
> 없다. 필요하다면 먼저 새로운 강한 참조를 얻어야 한다.

### 상태

`PyUnicode_CHECK_INTERNED(s)`로 조회하며
`_PyUnicode_STATE(s).interned`에 저장되는 인터닝 상태에는 다음 값이
있다.

- `SSTATE_NOT_INTERNED`: 0이다. 불리언 문맥에서도 유용하다.
- `SSTATE_INTERNED_MORTAL`: 1이다.
- `SSTATE_INTERNED_IMMORTAL`: 2다.
- `SSTATE_INTERNED_IMMORTAL_STATIC`: 3이다.

이 상태들 사이에서 허용되는 전이는 다음과 같다.

- 동적으로 할당된 문자열:

  - `0 → 1`: `_PyUnicode_InternMortal`
  - `1 → 2` 또는 `0 → 2`: `_PyUnicode_InternImmortal`

  동적 문자열에 `_PyUnicode_InternStatic`을 사용하는 것은
  오류다. 그 밖의 경우에는 상태가 바뀌지 않는다.

- 싱글턴은 런타임 초기화 때 `0 → 3`으로 인터닝된다. 그 이후에는
  어떤 인터닝 함수를 호출해도 상태가 바뀌지 않는다.

> **해설 — 상태 전이는 한 방향이다**
>
> 동적 문자열은 인터닝되지 않은 상태에서 소멸 가능한 인터닝
> 문자열이 되거나 곧바로 불멸 인터닝 문자열이 될 수 있다. 소멸
> 가능한 문자열을 나중에 불멸로 승격할 수도 있다. 반대로 불멸
> 문자열을 소멸 가능 상태로 되돌리는 전이는 없다. 정적 싱글턴의
> 상태 3은 처음부터 런타임 전체 수명을 갖는 객체임을 별도로
> 나타낸다.
