/goal RustPython 이슈 종료 요청 초안에 포함된 24건을 독립적으로 재검증하라.

목표는 기존의 “해결됐다”는 결론을 확인하는 것이 아니다. 원래 보고된 문제가 기준 커밋에서 해결됐는지, 제출하려는 초안의 구체적인 주장까지 새 실행 증거로 뒷받침되는지 판단하라. 종료 권고를 철회하거나 검증 불가로 남기는 것도 유효한 결과다.

이 작업은 로컬 검증과 새 보고서 작성까지만 수행한다. 버그 수정, 기존 보고서 수정, commit, push, 업로드, GitHub 이슈·PR·댓글 작성 및 이슈 닫기는 하지 않는다.

2. 독립 검증 방식

현재 대화 이력과 이전 판정 요약을 상속하지 않는 새 서브 에이전트 두 개를 호출하라.
지원되는 경우 fork_turns="none"을 사용한다.
기존 검증 에이전트를 재사용하지 않는다.

초기 전달 내용은 다음으로 제한한다.
- 담당 이슈 번호와 원문 URL
- 인터프리터 기준 커밋
- 검증 절차와 완료 조건
- 담당 실행 위치
- 보존·자원·외부 작업 제한
- 새 산출물 저장 위치

이전 판정, 성공 요약, 해결됐다는 전제, 기존 재현 코드의 기대 결과를 초기 메시지에 전달하지 않는다.

각 에이전트는 먼저 GitHub 이슈 본문과 범위에 영향을 주는 댓글을 읽고 다음을 기록하라.
- 원래 실패한 입력과 실행 경로
- 사용한 의존성·플랫폼·버전 조건
- 기대 동작
- 종료 판단에 필요한 최소 검증 범위
- 원문의 오타나 불완전한 예제
- 이슈의 현재 open/closed 상태와 조회 시각

이를 원문 기준 검증 계획으로 저장한 뒤 기존 제출 초안과 세부 보고서를 읽게 하라. 기존 보고서에서 재현 방법과 증거를 활용하되, 판정은 정답으로 취급하지 않는다.

초안을 읽은 후 각 주장과 필요한 검증을 대응시켜라.
원문 문제의 해결과 초안에 추가로 적힌 넓은 주장의 정확성을 별도로 평가한다.
이미 닫힌 이슈는 기술적 해결 여부와 별개로 추가 종료 요청이 필요한지 구분한다.

3. 사용할 수 있는 두 실행 위치

다음은 기존 실행 위치와 캐시의 후보 정보다. 실제 상태와 연결 관계를 읽기 전용으로 재확인한 후 사용하라.

실행 위치 A:
소스와 cwd:
 <workspace>

기존 빌드 디렉터리:
 <survey>/.build/slot-a

기존 실행 파일:
 위 디렉터리의 verification/rustpython

실행 위치 B:
소스와 cwd:
 <slot-b-source>

기존 빌드 디렉터리:
 <survey>/.build/slot-b

기존 실행 파일:
 위 디렉터리의 saved/current-f39-x86/rustpython

기존 리포트 워크트리:
 <report-worktree>

리포트 워크트리는 자료를 읽는 위치다. 세 번째 재현 실행 위치로 사용하지 않는다.

4. 자원 제한과 실행 큐

모든 빌드·재현·CPython 비교·PTY 실행·실행 파일 식별용 호출은 확인한 A/B 두 위치에만 큐잉한다.

- 각 실행 위치는 한 에이전트가 독점한다.
- 같은 위치에서 두 작업을 동시에 실행하거나 변경·빌드하지 않는다.
- RustPython과 CPython을 포함해 동시에 실행하는 검증 작업은 최대 두 개다.
- 각 에이전트는 자신의 위치에서 작업을 순차 실행한다.
- 부모 에이전트가 추가 실행할 때도 해당 위치를 인계받아 같은 큐를 사용한다.
- 디스크나 메모리가 부족하면 하나씩 실행한다.
- 새 clone, worktree, target 디렉터리, 가상환경, 컨테이너 또는 추가 빌드 환경을 만들지 않는다.
- 기본 전략은 기존 실행 파일과 설치된 의존성의 재사용이다.
- 빌드가 기존 바이너리·캐시를 덮어쓰거나 보존 조건을 위반한다면 빌드하지 말고 제약을 기록한다.
- 두 위치 중 하나만 안전하게 사용할 수 있으면 그 위치에서 순차 처리한다. 임의의 세 번째 위치를 만들지 않는다.

실행 시간과 의존성을 고려해 두 에이전트에 작업을 배분하라. 동일 이슈를 양쪽에서 중복 실행하는 것은 기본 요구가 아니다. 아키텍처 차이, 모순된 결과, 불안정한 동작을 확인할 필요가 있을 때만 추가 실행한다.

환경 식별은 위치별로 한 번 수집해 공유하고, 이슈별로는 그 식별 기록과 추가 조건을 참조하게 하라.

5. 기존 작업 보존

메인 소스, 모든 기존 워크트리, 커밋된 파일, 미커밋 변경, untracked 파일, 기존 보고서, 로그, 바이너리와 빌드 캐시를 삭제하거나 덮어쓰지 않는다.

reset, clean, cargo clean, 강제 checkout, 기존 작업 제거를 하지 않는다.
검증을 위해 테스트의 assertion·입력·기대값·skip·expectedFailure를 변경하지 않는다.
기존 재현 코드나 의존성 파일도 수정하지 않는다.

새 입력, 로그, 임시 파일과 보고서는 기존 자료와 구분되는 새 경로에 저장한다.
예:
 <workspace>/independent-verification/<현재시각>-closure24-f39b054/

이미 존재하면 다른 새 경로를 사용한다.
에이전트별 출력 디렉터리를 분리하고 같은 파일을 동시에 작성하지 않는다.

가능하면 -B와 PYTHONDONTWRITEBYTECODE=1을 사용한다.
REPL history, 임시 파일, 생성 결과도 새 경로로 격리한다.
단, 종료 동작을 검사하는 이슈에서 정상 종료 경로를 우회하지 않는다.

시작과 종료 시 Git 상태 및 기존 증거·입력의 해시를 대조한다.
직접 확인하지 않은 범위까지 “모두 보존을 검증했다”고 주장하지 않는다.

6. 환경과 실행 파일 식별

캐시가 있거나 git HEAD가 같다는 이유만으로 실행 파일도 기준 커밋이라고 가정하지 않는다.

다음을 새로 확인하고 기록하라.
- 소스 HEAD와 관련 미커밋 변경
- 실행 파일의 실제 경로, SHA-256, 버전 배너, 아키텍처
- 실행 파일과 기준 커밋을 연결하는 빌드·식별 근거
- 실제로 import된 표준 라이브러리의 경로와 기준 커밋과의 일치 여부
- CPython의 실제 버전, 경로, 아키텍처
- cwd, 관련 환경변수, locale 가용성과 실제 적용값
- 외부 의존성의 실제 버전과 로드된 경로

특히 B의 실행 파일이 A의 Lib를 먼저 읽을 수 있는지 확인하라.
식별 근거가 부족하면 그 한계를 남기고 기준 커밋의 확정 결과로 취급하지 않는다.

7. 이슈별 검증

각 이슈에 대해 다음 순서로 수행하라.

A. 원문과 초안의 주장 구분
원문 요구, 제출 초안의 주장, 기존 재현 코드가 실제 검사하는 범위를 대응시킨다.
초안에 “추가 입력도 통과”, “원본 테스트 전체 통과” 등이 적혀 있으면 그 주장도 검증 대상이다.

B. 새 실행
원래 실패 경로를 우선 재현한다.
필요한 의존성·locale·실행 모드를 맞춘다.
의미 있는 경우 CPython에 동일 입력을 전달한다.
실제로 실행한 파일을 저장하고 해시를 남긴다.

보고서에 표시된 코드와 보존된 실행 입력이 다르면 차이를 기록한다.
경로 치환이나 서식 변경이 동작을 바꾸지 않았는지 확인한다.
읽는 사람이 본문만 보고 재현할 수 있는지도 평가한다.

C. 최소 보강
원문 범위나 초안의 주장이 기존 입력보다 넓다면 그 차이를 확인하는 최소한의 테스트를 추가한다.
단순 import 성공, 속성 존재, generator 생성, 컴파일 성공만으로 실제 사용 경로의 성공을 주장하지 않는다.

D. 결과 판독
stdout, stderr, 종료 코드, timeout, 실제 assertion 결과를 함께 확인한다.
skip, expectedFailure, 테스트 0개 실행을 통과로 계산하지 않는다.
예상된 예외나 종료 코드 1을 무조건 실패로 처리하지 않는다.
timeout, 실행 차단, 빌드 실패, 환경 오류는 해결·미해결의 근거로 대체하지 않는다.

E. 과거와 변경 근거
과거 실패 기록과 새 결과를 비교한다.
재사용한 과거 증거와 이번에 실행한 증거를 명확히 구분한다.
과거 재실행을 위해 checkout이나 보존 조건을 위반하지 않는다.
관련 PR·커밋의 실제 변경이 관찰 결과를 설명하는지 확인한다.
관련 변경과 직접 실행해 확인한 최초 수정 커밋은 구분한다.
PR와 부모 커밋을 실행하지 않았다면 최초 수정 커밋을 확정하지 않는다.

8. 필수 오판 방지

- #2527: 실제 터미널/PTY REPL에서 원문 블록의 표현식 출력과 프롬프트를 확인한다. 스크립트나 compile(..., "single")만으로 대체하지 않는다.
- #3846: 실제 bytecode를 끝까지 순회하고 modulefinder를 실행한다. 초안의 원본 테스트 17개 통과 주장도 확인한다.
- #4506: SymPy 1.11.1·mpmath 1.2.1의 실제 로드 경로와 원래 실패했던 속성 처리 경로를 확인한다.
- #4527: 정상 인터프리터 종료 중 __del__ 출력과 stderr를 확인한다. os._exit로 종료를 우회하지 않는다.
- #4541: flag 값뿐 아니라 실제 sys.path와 import 가능 여부를 검사한다. script/-c/-m/REPL, 환경변수, -E/-I와 symlink 주장의 범위를 확인한다.
- #4762: 출력의 공백을 repr와 길이로 확인한다.
- #4769: 원문의 정수를 pickle하는 오타와 의도한 deque 객체 입력을 구분한다. protocol 0–5의 상태 보존과 원본 회귀 테스트를 확인한다.
- #4784: HTTP 200만 확인하지 않는다. 기준 커밋 README의 실제 목적지와 응답 본문의 crate/API 문서를 확인한다. 현재 외부 사이트 결과와 기준 커밋에서 빌드한 문서를 혼동하지 않는다.
- #4786: 원문 surrogate 입력을 보존한다. UnicodeEncodeError와 종료 코드 1이 기대 동작일 수 있다.
- #4856: 컴파일 panic 해결과 애플리케이션 실행 성공을 구분한다. 원본의 미정의 BaseFTests와 보정된 실행 예제를 별도 입력으로 다룬다.
- #4907: 컴파일과 실제 event loop에서의 await 완료를 구분한다.
- #4908: 단순 문자열 출력보다 재파싱 가능성과 AST 구조를 확인한다.
- #4950: 실제 locale과 검사한 format specifier 전체를 기록한다. C locale 결과를 모든 locale의 호환성으로 확대하지 않는다.
- #4970: 필요한 locale이 있는지 확인하고 LC_ALL이 실제로 unset인지 검사한다. C-locale fallback이나 skip을 통과로 처리하지 않는다.
- #5179: 메서드 존재뿐 아니라 버퍼 접근·쓰기·해제·export 중 크기 변경 차단과 해제 후 변경을 확인한다.
- #5656: 종료 코드뿐 아니라 경고의 발생·종류와 warning-as-error 동작을 확인한다.
- #5699: 네 blocker와 실제 uncaught exception의 ANSI 색상·제안 문구를 확인한다. 기대된 예외 종료를 crash로 분류하지 않는다.
- #6429: CPython과 RustPython의 빌드 설정값이 같아야 한다고 가정하지 않는다. 해당 RustPython 빌드에서 원문이 요구한 값의 정의와 의미를 확인한다.
- #8052: name/repr 외에 초안이 주장하는 alias와 JSON 회귀 테스트도 확인한다.
- #8494: classmethod와 staticmethod 양쪽의 두 annotation 속성에 대해 읽기·캐시·대입·삭제 및 원본 함수와의 독립성을 확인한다.
- 나머지 이슈도 원문과 초안에 적힌 추가 동작을 빠짐없이 확인한다.

9. 효율적인 진행과 실패 처리

작업 시작 시 이슈별 담당 슬롯과 실행 순서를 정하라.
관련 원문 조회·소스 읽기·메타데이터 수집은 가능한 범위에서 묶어서 처리한다.
짧은 재현과 환경 의존 검사를 먼저 실행해 장애를 조기에 발견한다.

각 실행에 타당한 timeout을 설정한다.
timeout이면 해당 프로세스를 종료·회수하고 로그를 남긴 뒤 다른 이슈를 진행한다.
원인이나 조건이 바뀌지 않은 동일 실패를 반복하지 않는다.
결과가 불안정하면 반복 횟수와 성공·실패를 모두 기록한다.

문제가 없는 최소 재현을 불필요한 전체 테스트나 전체 빌드로 확대하지 않는다.
다만 초안에 명시된 원본 테스트나 추가 동작은 생략하지 않는다.
검증하지 못한 주장은 확인된 주장으로 남기지 않는다.

10. 판정

기술적 판정은 이슈마다 다음 중 하나를 사용한다.

- 해결 확인: 원문 요구 범위를 충족하는 새 실행 증거와 해결 근거가 충분함.
- 부분 해결: 일부 동작은 해결됐지만 원문 전체를 충족하지 못함.
- 미해결: 원래 문제가 기준 커밋에서도 재현됨.
- 검증 불가: 환경·도구·식별·증거 부족으로 결론을 내릴 수 없음.

별도로 제출 초안의 처리 권고를 기록한다.

- 유지: 종료 권고와 본문 주장이 모두 뒷받침됨.
- 문구 축소·수정: 종료 근거는 충분하지만 일부 추가 주장이 과장됐거나 검증되지 않음.
- 종료 권고 철회: 원문 범위의 미해결 문제가 남음.
- 보류: 종료를 권고할 증거가 부족함.
- 종료 요청 불필요: 이미 닫힌 이슈 등으로 추가 요청이 필요 없음.

원문 해결 여부와 초안 문장의 정확성을 하나의 판정으로 뭉개지 않는다.

11. 산출물

새 결과 경로에 다음을 작성하라.

- SUMMARY.md
  유지 가능한 종료 권고 수와 목록.
  문구 수정이 필요한 항목과 수정안.
  철회·보류·종료 요청 불필요 항목과 이유.
  기존 초안과 결론이 달라진 항목.
  직접 재실행한 증거와 재사용한 증거의 구분.
  기존 작업 보존 확인 범위.

- cases/<번호>/README.md
  원문 요구와 초안 주장.
  기술적 판정과 초안 처리 권고.
  실제 실행 입력과 명령.
  환경·실행 파일·소스·Lib 식별 기록.
  기대·실제 결과, stdout/stderr, 종료 코드, timeout.
  과거 비교, 관련 변경, 검증 한계.
  필요한 입력·명령·핵심 출력은 본문에 포함한다.
  표와 접기 영역은 사용하지 않는다.
  이전 대화 문맥이나 내부 작업 서술은 제외한다.
  원본 로그 링크는 보충 자료로 둔다.

- 기계 판독 가능한 실행 기록
  실행 ID, 이슈 번호, 슬롯, argv, cwd, 관련 환경변수,
  입력 해시, 실행 파일 식별, 시작·종료 시각,
  stdout/stderr 경로, 종료 코드, timeout, 판정 근거.

기존 제출 초안과 세부 보고서를 직접 수정하지 않는다.
필요한 본문 수정안은 새 산출물에만 작성한다.

12. 완료 조건

24건 모두 기술적 판정과 초안 처리 권고가 있어야 한다.
각 판정에는 새 실행 근거 또는 구체적인 검증 불가 사유가 있어야 한다.
초안의 핵심 주장 중 확인하지 못한 부분이 표시돼야 한다.
기존 작업 보존 여부와 확인 범위가 기록돼야 한다.

24건 모두 해결됐다는 결론을 만드는 것은 완료 조건이 아니다.
완료 시 실제로 종료를 권고할 수 있는 개수와 목록을 새 근거에 따라 보고하라.
